# TransitGo — 商業化產品藍圖與平台規劃

> 狀態：規劃文件，**不含任何程式變更**（沒有新資料表、API、UI、billing、支付、會員系統）。
> 事實來自目前的程式碼（見 §1）；市場、價格、客戶需求都是**假設**，需靠訪談驗證。
> 前提：單人開發、未來可能成為團隊、沒有法務、第一個客群 = 竹北（細節見 [zhubei-business-commute.md](zhubei-business-commute.md)）。

## 1. 現況盤點（已有／缺少／可重用／要拆分／可商業化）

### 已有（程式碼中真實存在）
| 層 | 內容 |
|---|---|
| iOS App | 首頁（最近公車站／YouBike）、搜尋、路線規劃、即時導航（TripEngine）、附近（公車／YouBike／捷運／地標）、收藏與常用旅程（SwiftData，本機）、車票匯入與提醒、Live Activity／小工具 |
| 路由核心 | 統一圖：公車、捷運（4 個營運商）、台鐵、高鐵、YouBike、步行、虛擬起終點；時間相依 A*；排序；即時疊加（公車到站、台鐵誤點、捷運）；圖 84,587 節點／420,128 邊，存 Supabase Storage |
| 後端 | Express + Postgres（Supabase）；裝置註冊與 APNs 推播、公告、回報、路線評分、觀測、地標與地點評論（含檢舉）、測速照相、`/admin` 管理頁（受 ADMIN_TOKEN 保護）、`/api/v1/routes`、`/v1/realtime/*`、`/v1/bike/*`、`/v1/routing/coverage`、圖重建 |
| 部署 | Render 免費方案（512 MB）；閒置 ~315 MB；Supabase Postgres／Storage |

### 缺少（對商業化而言）
- **沒有帳號／租戶／角色**：只有匿名裝置 token；沒有公司、學校、營運商的概念。
- **沒有 API key／用量計量／限流／SLA**：`/api/v1/routes` 是 App 內部用，沒有對外契約。
- **沒有跨裝置資料**：收藏與旅程只在本機。
- **沒有票價資料**（`fare = null`）。
- **公車無誤點秒數、高鐵無即時、YouBike 時間是估算**。
- **資料來源單一且額度極小**：TDX 金鑰實測每分鐘 5 次（見 §9），且 App 內嵌金鑰直接呼叫。
- **沒有營運觀測**（錯誤率、延遲、用量儀表）；記憶體只有 `/v1/health`。
- **沒有法務文件**：隱私政策、服務條款、資料處理協議都沒有經過專業審閱。

### 可重用
路由引擎與圖、即時疊加、推播、公告、管理頁骨架、評論／檢舉流程（可改為企業內部回報）。

### 需要拆分
| 現在 | 應拆成 |
|---|---|
| iOS App 直接打 TDX | App → 自家後端 → TDX（金鑰與額度集中管理、可快取） |
| 單一 Express 程式 | 對外 API（路線／即時）與內部管理（admin／推播）分開路由與認證 |
| `/admin` 單一 token | 依角色（平台管理員／企業管理員）的後台 |
| 圖在記憶體 | 之後若流量成長，路由服務獨立成一個可水平擴充的服務 |

### 適合商業化（依可行性排序）
1. 企業通勤頁（重用路由＋即時，缺租戶）——最近、最單純。
2. Premium 個人功能中「智慧提醒」（推播已存在）。
3. Routing API（需先解決 TDX 額度與 SLA，短期不適合）。
4. 校園、B2G：需要法務與更長銷售週期，短期不做。

## 2. 產品定位

**Product Vision**：讓在台灣的每一趟大眾運輸移動（含最後一哩的 YouBike 與步行）都能事先知道「幾點出門、怎麼轉、現在有沒有車」。

**Product Mission**：把分散在公車、捷運、台鐵、高鐵、YouBike 的公開資料，整合成**一個可信的決策**，並老實標示哪些是即時、哪些是時刻表、哪些只是估算。

**Core Value（我們真正比別人強的地方，來自現有系統）**
1. 多模式混合路線（含 YouBike 有車／有位的即時判斷），不是單一模式查詢。
2. 資料誠實標示（沒有票價就是沒有；估算就標估算）。
3. 從路線到導航到提醒是同一條鏈（收藏 → 規劃 → 導航 → Live Activity）。

**Target Users**：① 通勤族（固定路線、在意準時）；② 企業人資／行政（幫員工解決「怎麼來公司」）；③ 之後才是學校、營運商、政府。

**Business Model（假設，待驗證）**：個人 Premium 訂閱（小額）＋企業月費（依人數分級）＋之後的 API 用量計費。不賣個資、不做廣告。

### 平台分層
```text
Consumer App     iOS App（B2C 入口，也是企業員工的入口之一）
Admin/Dashboard  Web 後台：平台管理員、企業管理員（分角色）
Backend Platform 租戶、認證、通知、資料存取（新增）
API              對外 Routing／Realtime API（穩定契約、金鑰、限流）（之後）
Data Platform    TDX／GTFS 攝取、圖建置、快取、用量與品質觀測
```
原則：Consumer App 不放企業／校園專屬邏輯；企業功能以「公司頁＋後台」承載，App 只提供收藏模板等通用能力。

## 3. B2C 與 Premium

### 現有 B2C 整理
首頁（最近站牌／YouBike）、搜尋、路線、導航、附近、即時、收藏、常用旅程——都已可用（未在真機驗證）。**這些基本功能應永遠免費**：它們是獲客與口碑來源。

### Premium 候選：每項回答「使用者為什麼願意付費？」

| 功能 | 使用者為什麼付費 | 我的判斷 |
|---|---|---|
| **智慧提醒**（「該出門了」：依即時班次與步行時間倒推、延誤時提前叫你） | 直接省下等車與趕不上的損失；每天用；推播與 Live Activity 已有基礎 | **最值得付費**。但「提醒」若只是提醒發車時間，免費即可；付費的是「依即時狀態動態調整」 |
| **跨裝置同步**（收藏、常用旅程） | 換手機／多裝置不想重設 | 中等。用 iCloud（CloudKit）同步成本低且無需自建帳號；**建議免費**，不要為此做會員系統 |
| **進階路線偏好**（少轉乘／少步行／避開特定路線） | 個別使用者確有偏好 | 弱。排序已支援不同目標，基本偏好應免費；不建議收費 |
| **進階旅程**（多停靠點、週期性通勤、出發時間視窗） | 通勤族每天固定路線 | 中等，**需求未驗證**；可與智慧提醒綁成一個「通勤」方案 |
| **旅程統計**（本月搭乘、花費、節省時間） | 好奇心、報帳 | 弱。且**沒有票價資料**，花費統計目前做不到；個人搭乘統計涉及隱私，先不做 |
| **通知**（誤點、停駛、公告） | 核心價值 | **不應收費**；基本通知免費，收費只在「客製化規則」 |

**建議**：先只驗證一個付費點——「通勤方案」（智慧動態提醒＋固定路線＋Live Activity）。在有用戶說「我會付錢」之前，不做付費牆、不做 billing。

## 5. B2B — TransitGo Campus（校園交通）

**結論：現階段不做，先只寫下邊界。**

| 功能 | 可行性 | 限制 |
|---|---|---|
| 校園周邊到站資訊、上下學路線頁 | 技術上可（同企業頁） | 用於大學生／成人可行；**對未成年人要另評估** |
| 校車／校園接駁 | 需即時位置與營運方 | 與企業接駁同樣不做 GPS |
| **家長通知、追蹤學生位置** | **不做** | 涉及未成年人位置與個資、家長同意、學校責任；**沒有法務不得處理** |

**先決條件**：取得專業法務意見（未成年人個資、家長同意、資料保存），且企業版已有付費客戶。否則不啟動。

## 8. 商業與營運風險（老實列出）

1. **資料依賴**：所有即時資料來自 TDX；額度、條款、穩定性都不在我們手上。
2. **單人維運**：正式環境已發生兩次 OOM；免費方案有休眠與冷啟動，企業客戶不能接受。→ 收第一筆錢之前要升級並有基本監控。
3. **法務空白**：隱私政策、服務條款、資料處理協議都沒有專業審閱。
4. **需求未驗證**：本文所有客戶輪廓與價格都是假設。
5. **記憶體天花板**：圖載入後 ~190 MB，再加資料需升級方案。

## 9. 已知的阻塞問題：TDX 額度

2026-09-20 實測：所有 TDX 資料端點回 `x-ratelimit-limit-minute: 5`（token 端點 20／分鐘），額度耗盡時 HTTP 429。
影響：App 首頁每 20 秒直接呼叫 TDX 無法運作；後端即時查詢回「no_data」。
待確認：①這把金鑰的方案／限制（TDX 會員中心）；②限流是依金鑰或依 IP。
建議方向：站牌位置是靜態資料，後端圖已載入，**由後端提供「最近站牌」**，並以快取共用即時查詢，讓 App 幾乎不用打 TDX，同時移除 App 內嵌金鑰。

## 10. 需要使用者決定的事

1. 是否先做 Phase 0.5（後端提供最近站牌）——它同時是所有後續功能的基礎。
2. 訪談對象的取得方式（你的人脈？竹北園區窗口？）。
3. Premium 是否只驗證「通勤方案」這一項。
4. 何時升級 Render（建議在第一個試用客戶之前）。
